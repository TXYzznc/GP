## Context

当前项目使用 Unity GameFramework 框架，包含 Procedure 系统、Event 系统、UI 系统等。音频管理需要与这些系统紧密集成。

项目有以下约束：
- 所有异步操作必须使用 UniTask（不用协程）
- UI 音效播放需要在 UIForm 打开/关闭时触发
- 战斗系统需要支持动态 BGM 切换（普通/Elite/Boss 三级战斗 BGM）
- 资源加载走 GF.Resource 系统
- 配置表数据走 DataTable（由 DataTableGenerator 自动生成）
- 所有日志输出使用 DebugEx

## Goals / Non-Goals

**Goals:**
- 实现统一的音频管理中枢 (AudioManager)，支持全生命周期管理
- BGM 实现平滑淡入淡出切换（消除声音突跳）
- SFX 使用对象池优化性能（播放延迟 < 50ms）
- 支持 4 轨独立音量控制（BGM/SFX/环境音/语音）
- 音量设置支持持久化（PlayerPrefs 存储）
- 支持 3D 音效定位（可选，为后续扩展预留）
- 与 Procedure、Event、UI 系统完整集成
- 所有音效参数通过 DataTable 配置化（无硬编码）

**Non-Goals:**
- 实时音频生成或 DSP 效果处理
- 音频压缩编解码（使用 Unity 原生支持）
- 网络音频流（本地资源加载）
- 混音器预设链（Unity AudioMixer）
- 角色语音系统（可在此基础上扩展，但不在本期实现）
- 动态 BGM 混搭（战斗进度触发 BGM 层级变化）

## Decisions

### 1. 系统架构：分层模块设计

**决策**: AudioManager 为总管理器，下管 BGMManager、SFXManager、VolumeManager、AudioResourceManager 四个专职模块

**理由**: 
- 单一职责原则，每个模块职责清晰
- 易于扩展（例如后续加入语音系统时只需新增 VoiceManager）
- 易于测试和维护

**替代方案考虑**:
- ❌ 单一庞大的 AudioManager：会导致代码冗长，职责混杂
- ❌ 完全分散式（每个模块自己管理音效）：无法统一控制音量、缓存等

### 2. BGM 切换机制：队列 + 淡入淡出

**决策**: BGM 采用队列管理，支持淡出→切换→淡入三步流程

**理由**:
- 场景切换时需要平滑的音乐过渡（不能突然停止或启动）
- 可支持多个 BGM 排队等待的场景（例如战斗结束时已有新场景的 BGM 在队列中）
- 淡入淡出时长可配置，易于调整感受

**替代方案考虑**:
- ❌ 硬切换：声音不自然，用户体验差
- ❌ 交叉淡化（同时播放两个 BGM）：增加复杂度，且不符合游戏音乐习惯

### 3. SFX 管理：对象池缓存

**决策**: SFX 使用对象池模式，为每个 SFX ID 维护一个 AudioSource 池

**理由**:
- UI 音效频繁触发（每次按钮点击），直接创建销毁 AudioSource 会产生性能抖动
- 对象池可复用 AudioSource，避免内存碎片化
- 预先分配固定数量可控制内存占用

**替代方案考虑**:
- ❌ 每次都创建新 AudioSource：性能差，尤其在大量UI操作时
- ❌ 全局对象池：无法区分不同 SFX 的状态，难以精准控制

### 4. 音量管理：分轨独立控制

**决策**: 实现 4 轨独立音量（BGM/SFX/环境音/语音），每轨有独立调节器，整体受主音量调控

**理由**:
- 玩家偏好不同（有人喜欢听背景音乐，有人只要 SFX 反馈）
- 流媒体/视频通话时需要快速静音某些轨道
- 公式: `最终音量 = 主音量 × 轨道音量 × 是否静音`

**替代方案考虑**:
- ❌ 全局单一音量：用户控制粒度不足
- ❌ 无持久化：每次启动游戏音量重置，用户体验差

### 5. 资源加载策略：BGM 流式，SFX 缓存

**决策**: 
- BGM：流式加载（不存储在内存中），直接播放时加载
- SFX：预加载并缓存到对象池

**理由**:
- BGM 时长长（2-3分钟），一次只播一个，无需全部在内存中
- SFX 时短（0.2-0.8秒），频繁触发，缓存避免反复加载
- 内存占用可控（BGM ~2-5MB/个，SFX ~50KB/个）

**替代方案考虑**:
- ❌ BGM 也缓存：浪费内存，尤其是 23 个 BGM
- ❌ SFX 都流式加载：每次播放都加载延迟高

### 6. 配置表驱动

**决策**: 所有音效参数（路径、音量、Pitch、3D/2D、循环等）通过 AudioClipTable.xlsx 配置

**理由**:
- 无需改代码就能新增/修改音效参数
- 便于非程序人员（策划/音效师）管理
- 运行时可热更新配置

**替代方案考虑**:
- ❌ 硬编码 ID 和参数：每次改参数都要改代码重编译

### 7. 与 GF 系统集成：事件驱动

**决策**: 通过 GF.Event 事件系统进行模块间通信

**理由**:
- 符合项目现有架构
- 解耦 AudioManager 与业务系统
- 易于追踪调试（事件日志）

**集成点**:
- Procedure 切换 → 触发 BGM 变更
- 战斗开始 → 播放战斗 BGM + 战斗开始音效
- 战斗胜负 → 播放胜利/失败音效
- UI 打开/关闭 → 播放对应音效

## Risks / Trade-offs

| 风险 | 影响 | 缓解方案 |
|-----|------|---------|
| **BGM 切换延迟** | 玩家感受到音乐断层 | 调优淡出淡入时长（0.5-1s），提前预加载 |
| **SFX 对象池溢出** | 大量 UI 点击导致音效播放不出 | 初始化时根据 SFX 使用频率预估池大小 |
| **内存峰值** | 多个 BGM 同时加载 | BGM 采用流式加载，不存储完整内容 |
| **3D 音效性能** | 大量 3D 音效计算代价大 | 限制同时 3D 音效数量，或使用更新距离衰减 |
| **配置表错误** | 找不到音效资源导致运行时崩溃 | 加载时验证配置表完整性，缺失资源提供降级方案 |
| **协程与 UniTask 混用** | 时序混乱 | 所有异步操作统一使用 UniTask |

### Trade-offs:

- **淡入淡出 vs 响应速度**: 淡入淡出需要时间（最低 0.5s），不能做到毫秒级切换。折衷：提供 IsImmediate 参数允许硬切换（特殊情况如Debug）
- **对象池大小 vs 内存**: 对象池越大越安全，但占用更多内存。折衷：根据使用场景动态调整（高频 UI 音效池大 10，低频特效音池小 3）
- **流式加载 vs 缓存**: BGM 流式节省内存，但如果需要无缝切换两首 BGM 会增加复杂度。折衷：支持预加载 API，必要时由使用方手动预加载

## Migration Plan

**部署阶段**:
1. 创建 AudioManager 系统代码（Phase 1）
2. 新增 AudioClipTable 配置表并填充所有音效
3. 整合到 Procedure 和 Event 系统（Phase 2）
4. 逐个场景和 UI 接入音效调用（Phase 2）
5. 性能测试和内存优化（Phase 3）

**回滚策略**:
- AudioManager 是新增系统，移除不会影响现有功能
- 所有接入点都通过 try-catch 保护，防止音效系统异常影响主流程
- 可快速禁用：`AudioManager.Instance.SetMasterVolume(0)` 全静音

## Open Questions

1. **角色语音系统**：是否在 Phase 1 实现，还是留作 Phase 4 的扩展？
   - 当前计划：留作扩展，本期只预留 VoiceTrack

2. **动态 BGM**：战斗中是否需要根据进度/形势动态切换 BGM 层级？
   - 当前计划：不在本期，可作为后续高级功能

3. **音效压缩格式**：BGM 用 MP3 还是 OGG？
   - 建议：OGG（压缩率好，流式播放友好）

4. **3D 音效精度**：是否需要支持 HRTF 空间音频？
   - 当前计划：不需要，基础 3D 定位即可

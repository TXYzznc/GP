## Context

项目知识库的 outputs 文件夹存有 99 个 .md 文件，包括：
- 配置表生成指南和问题分析文档
- 各种系统设计方案和修改清单
- 临时测试指南和快速参考
- 数值系统设计的多个版本
- 绘图提示词和图片参考资料
- 各种bug修复报告和实现验证文档

这些文件缺乏组织，存在重复、过时内容混杂的问题。需要通过系统化的三阶段处理流程进行重索引。

## Goals / Non-Goals

**Goals：**
- 将 99 个文件分析并重写，提升文档质量和可用性
- 识别重复和过时内容，进行合并或删除
- 建立清晰的 wiki 分类结构，提高文档可查找性
- 更新 INDEX.md，建立新的索引体系
- 实现可并行处理的任务拆分，提高效率

**Non-Goals：**
- 不修改 wiki 和 raw 文件夹中的现有文件
- 不改变项目的代码或配置

## Decisions

### 决策 1：三阶段流程设计
**方案**：初步处理 → 二次处理 → 归纳和索引

**理由**：
- 初步处理阶段逐个深入分析文件，确保质量
- 二次处理阶段基于初步结果进行智能合并，避免重复
- 最后阶段集中进行分类和索引，降低复杂度

**替代方案**：一步到位直接分类 - 风险：容易忽略重复文件，降低合并质量

### 决策 2：并行处理拆分
**方案**：将 99 个文件分成 3-4 个工作组（每组 25-35 个文件），由不同 agent 并行处理

**理由**：
- 每个 agent 处理一个文件组的初步处理任务
- 文件组之间互相独立，适合并行
- 后续二次处理和索引统一在主进程中进行

**替代方案**：逐个处理所有 99 个文件 - 风险：耗时过长，效率低下

### 决策 3：元数据追踪
**方案**：在初步处理过程中，每处理完一个文件就在元数据文档中记录（文件索引、内容摘要、文件类型）

**理由**：
- 便于二次处理阶段快速扫描和去重
- 减少重复阅读同一文件的成本
- 为最终索引提供清晰的基础数据

**替代方案**：初步处理完全后再整理元数据 - 风险：容易遗漏细节，工作量更大

### 决策 4：wiki 分类结构
**方案**：按照功能系统进行分类放置
- 战斗系统相关 → `wiki/战斗系统/`
- 配置表相关 → `wiki/开发资源/配置表/`
- UI系统相关 → `wiki/UI系统/`
- 数值系统 → `wiki/数值系统/`
- 其他资源 → `wiki/开发资源/`

**理由**：与现有 INDEX.md 的分类体系保持一致，便于查找

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|--------|
| 文件分组时遗漏或不均匀 | 先完整列出所有文件，按大小和类型均匀分配 |
| 并行处理时重复分析同一文件 | 在元数据文档中明确标注每个文件的指派agent |
| 二次处理时难以判断文件是否过时 | 阅读wiki中的相关文档进行对比判断 |
| 最终索引时某些文件难以分类 | 允许存放到"杂项"类别，后续手动调整 |

## Migration Plan

1. **初步处理阶段**：各 agent 并行处理文件组，生成元数据文档
2. **汇总**：主进程汇总所有元数据，识别重复和过时文件
3. **二次处理阶段**：主进程处理合并、删除和更新
4. **归纳和索引阶段**：主进程将文件分类放入 wiki，更新 INDEX.md
5. **验证**：检查所有文件正确放置，INDEX.md 完整有效

# 论文文本内容修改指南

## 修改 2: 补充缺失的中等数据 

### 批注位置
在第一章背景介绍部分，数据层级划分处

### 问题分析
现有数据重复，缺少完整的层级划分，通常出现在以下场景：
- 游戏类型分类（只有高级分类，缺中等分类）
- 数值等级划分（只有高低端，缺中端）
- 功能复杂度分类（不够均衡）

### 修改方案

**原文示例（需根据实际文档调整）:**
```
游戏类型分为：回合制 RPG、自走棋、Roguelite...
```

**修改后:**
```
游戏类型按竞争模式分类如下：

1. 竞技型游戏（高竞争度）
   - 回合制竞速对战
   - 实时多人对战
   
2. 策略型游戏（中等竞争度）  ← 这是补充的中等分类
   - 自走棋（Auto Battler）
   - 卡牌构筑战斗
   
3. 探索型游戏（低竞争度）
   - Roguelite 探险
   - 剧情冒险

混合型游戏则结合多个类型的特点...
```

### 文字修改步骤

1. **定位原文** - 找到数据重复的段落
2. **识别规律** - 确定数据的自然分类（通常为 3-5 级）
3. **补充中间层** - 在高级和低级之间添加中等分类
4. **确保均衡** - 每个层级的项目数量大致相等
5. **验证逻辑** - 确保新增分类符合业务逻辑

### 验收标准
- [ ] 分类达到 3 层或以上
- [ ] 每层级至少 2-3 个项目
- [ ] 新增内容不产生重复
- [ ] 逻辑结构清晰

### 问题分析

### 修改方案

**原文示例:**
```

```

**修改后:**
```
本项目采用 GameFramework 框架作为底层架构支撑，其核心模块包括：

【GameFramework 核心模块】

1. 事件系统 (Event System)
   - 职责：系统间的事件驱动通信
   - 实现：发布-订阅模式
   - 应用：游戏状态变化、战斗事件触发

2. 资源管理系统 (Resource Manager)
   - 职责：游戏资源的加载、缓存、卸载
   - 实现：资源池、异步加载
   - 应用：Prefab、音频、纹理的管理

3. UI 框架 (UI Framework)
   - 职责：UI 生命周期管理、显示/隐藏控制
   - 实现：UIForm 基类、管理器模式
   - 应用：所有 UI 面板的统一管理

4. 实体系统 (Entity System)
   - 职责：游戏对象生命周期管理
   - 实现：Entity 基类、组件模式
   - 应用：角色、敌人、装饰物等游戏对象

5. FSM 有限状态机 (Finite State Machine)
   - 职责：状态转换管理
   - 实现：状态类、事件触发转换
   - 应用：游戏流程、战斗阶段的状态控制

【与项目系统的关系】

游戏业务系统（战斗、探索、背包等）构建在 GameFramework 提供的基础设施之上：
- UI 系统 → 依赖 UI Framework 的生命周期管理
- 战斗系统 → 依赖事件系统实现模块间通信
- 游戏流程 → 依赖 FSM 实现状态转换
- 资源加载 → 依赖资源管理系统的异步加载

这种分层设计使得业务系统专注于游戏逻辑，而 GameFramework 负责提供稳定可靠的基础设施...

4. **展示关系** - 说明业务系统如何依赖框架

## 修改 5: 明确设计重点

### 批注位置
某个关键设计决策处（具体位置需打开论文查看）

### 问题分析
原文提到某个设计方案，但没有清楚说明为什么这样设计，以及这样设计的优势。

### 修改方案

**原文示例（需找到实际位置）:**
```
伤害计算采用多套公式...
```

**修改后:**
```
伤害计算系统采用"多套公式"设计的关键考虑：

【设计选择：多套伤害公式（vs. 单一公式）】

原因分析：
1. 游戏平衡性需求
   - 单一公式难以区分不同伤害类型的特色
   - 多套公式允许对物理、法术、真伤分别调配
   - 实现"克制"机制（某些属性对某类伤害特别有效）

2. 可扩展性考虑
   - 新增伤害类型时，只需添加新公式
   - 不需要修改核心计算逻辑
   - 易于维护和调试

3. 性能权衡
   - 虽然多套公式增加计算量，但通过以下优化确保性能：
     * 预计算常用系数
     * 使用查表法替代复杂计算
     * 在关键帧缓存计算结果

【实现方案】
公式存储于 DamageFormulaTable（Excel 配置表），程序在运行时：
1. 根据伤害类型选择对应公式
2. 使用数据表查询系数
3. 执行计算并缓存结果

【权衡说明】
优势：灵活、可扩展、易调试
劣势：计算量稍大、配置表管理复杂
结论：收益 > 成本，推荐采用

相比之下，单一公式虽然简单，但不足以满足游戏的平衡需求...
```

### 文字修改步骤

1. **明确设计选择** - 说明采用的是什么方案
2. **分析设计原因** - 从 3-4 个角度解释为什么这样做
   - 功能需求（能做什么）
   - 可维护性（便于修改）
   - 性能考虑（不能太重）
   - 扩展性（便于添加新功能）
3. **说明实现** - 简要说明如何实现
4. **权衡说明** - 优劣对比
5. **对标方案** - 与其他方案对比，说明为什么选这个

### 补充内容模板

```
【设计选择：[方案名称]】

原因分析：
1. [角度1]：[说明]
2. [角度2]：[说明]
3. [角度3]：[说明]

实现要点：[简要说明如何实现]

权衡分析：
- 优势：[列举2-3个]
- 劣势：[列举1-2个]
- 结论：[为什么选这个]
```

## 修改 6: 补充框架模式与范例

### 批注位置

```

**修改后（先模式，再范例）:**
```
Buff 系统的设计模式与实现

【模式框架：组件模式】

组件模式的基本思想：
- 每个 Buff 是一个独立的组件
- 在需要 Buff 效果的对象上添加组件
- 组件通过生命周期方法（初始化、更新、销毁）实现功能

架构示意：
```
GameObject (棋子/敌人)
├─ StatComponent (基础属性)
├─ BuffComponent (Buff 管理)
│  ├─ FireBuff (燃烧 Buff 组件)
│  ├─ FreezeBuff (冰冻 Buff 组件)
│  └─ ...更多 Buff
└─ ...其他组件
```

【范例 1：配置表定义】

BuffTable（配置表）示例行：
```
BuffId | BuffName | EffectType | Duration | Param1 | Param2
001    | 燃烧     | DOT        | 3        | 10     | 0.5
002    | 减速     | DEBUFF     | 2        | 0.3    | 0
003    | 增伤     | BUFF       | 5        | 1.2    | 0
```

【范例 2：应用流程】

当技能触发 Buff 时：
1. 技能系统调用 `ApplyBuff(targetEntity, buffId)`
2. BuffComponent 在 BuffTable 中查询 BuffId
3. 根据配置创建 Buff 实例
4. Buff 开始执行（执行周期效果、图表提示等）
5. 时间到期后自动销毁

具体代码伪码：
```
class BuffComponent {
    public void ApplyBuff(int buffId) {
        BuffData data = BuffTable.Get(buffId);
        BaseBuff buff = BuffFactory.Create(data);
        activeBuff.Add(buff);
        buff.OnApply(this);
    }
    
    public void Update() {
        foreach(var buff in activeBuff) {
            buff.OnUpdate();
            if(buff.IsExpired()) {
                buff.OnRemove(this);
                activeBuff.Remove(buff);
            }
        }
    }
}
```

【范例 3：具体 Buff 实现】

如"燃烧" Buff 的实现：
- 初始化时：增加视觉特效（火焰光圈）
- 更新时：每隔一定时间（配置表的 Param2）造成伤害（Param1）
- 销毁时：移除特效

【优势说明】
- 模块化：每个 Buff 独立，易于添加新 Buff
- 可配置：通过表格调整 Buff 参数，无需改代码
- 易测试：可单独测试每个 Buff 的效果
- 易维护：Bug 修复只影响相关 Buff 组件

这种设计在项目中已应用于... [其他系统示例]
```

## 注意事项

### 通用原则
1. **保持学术严谨** - 不使用过于口语化的表述
2. **层级清晰** - 使用列表、编号、缩进展示层级关系
3. **数据准确** - 所有提及的模块、表、字段名都要与项目实际相符
4. **长度适宜** - 每个修改不应过短（至少 3-5 行）也不应过长（一次修改建议 20-30 行内）
5. **配置表关联** - 尽量关联项目中实际存在的配置表名称

### 修改验证
完成每个修改后，应该逐项验证：
- 内容与项目架构相符
- 没有产生重复
- 没有与其他章节冲突
- 文字表述清晰通顺
- 格式与论文整体风格一致

## 摘 要

随着游戏产业发展，融合多种玩法的复合型游戏逐渐成为市场主流，但现有产品在系统架构设计、玩法协同与可扩展性方面仍存在不足。本文设计并实现了一款基于Unity引擎的多玩法融合游戏——Clash of Gods，融合RPG、Roguelite、搜打撤、自走棋、卡牌策略五种玩法机制。

系统以GameFramework框架为底层架构，采用事件驱动与模块化设计思想，实现了战斗、物品背包、策略卡、探索四大核心系统。战斗系统基于自走棋机制，棋子由AI自动执行目标选择与攻击，配合完整的Buff效果系统和多类型命中检测；物品背包系统支持四类物品、堆叠机制与拖拽交互；策略卡系统通过配置表驱动与命令模式实现灵活扩展；探索系统实现了五状态AI状态机与双层视野检测。

技术层面，系统以Excel配置表管理全部游戏数据，实现策划与程序分离；以UniTask统一异步编程，以DOTween实现UI动效，以对象池降低运行时GC开销。经测试，游戏在主流PC配置下帧率稳定在60 FPS，内存峰值350MB，功能覆盖率100%。

本研究为多玩法融合游戏提供了一套可落地的架构方案，对系统模块化设计与性能优化具有参考价值。

**关键词：** 多玩法融合游戏；Unity引擎；GameFramework；自走棋；系统架构设计

## ABSTRACT

With the rapid development of the game industry, hybrid games combining multiple gameplay mechanics have become mainstream. However, existing products still have deficiencies in system architecture, gameplay synergy, and scalability. This paper designs and implements a multi-genre hybrid game called *Clash of Gods* based on Unity, integrating RPG, Roguelite, Extraction, Auto Battler, and Card Strategy mechanics.

The system uses GameFramework as the underlying architecture, adopting an event-driven and modular design approach to implement four core systems: combat, inventory, strategy card, and exploration. The combat system is based on an auto-battler mechanism with AI-controlled chess pieces, a complete Buff system, and multiple hit detection methods. The inventory system supports four item types, stacking, and drag-and-drop interaction. The strategy card system achieves flexible extension through configuration-table-driven design and the Command Pattern. The exploration system implements a five-state AI state machine and dual-layer vision detection.

Technically, all game data is managed through Excel configuration tables to separate design from programming. UniTask handles all asynchronous operations, DOTween drives UI animations, and object pooling reduces runtime GC overhead. Testing confirms a stable 60 FPS on mainstream PCs, peak memory usage of 350MB, and 100% functional test pass rate.

This research provides a practical architectural solution for multi-genre hybrid game development, with reference value for modular system design and performance optimization.

**Keywords:** Multi-genre Hybrid Game; Unity Engine; GameFramework; Auto Battler; System Architecture Design

### 1.1 研究背景

**多玩法融合游戏发展现状**

单一玩法游戏已难以满足玩家多元化需求。近年来，融合肉鸽、自走棋、搜打撤、卡牌等机制的复合型游戏逐渐成为市场主流。《哈迪斯》《杀戮尖塔》《逃离塔科夫》等代表作通过有机融合不同玩法机制，在全球范围内获得广泛认可，国内的《枪火重生》《元气骑士》等产品同样验证了多玩法融合设计的市场潜力。

然而，多玩法融合游戏面临显著的技术挑战：系统间耦合度高导致维护困难；初期设计未考虑扩展导致后续重构代价高；策划与程序高度耦合降低迭代效率；战斗场景同时处理大量实体与计算逻辑带来性能压力。

**游戏开发技术发展趋势**

Unity引擎凭借跨平台能力与活跃的生态，成为中小型团队的首选。数据驱动开发模式通过将游戏数据与代码分离，使策划可独立调整参数，大幅提升迭代效率。模块化与组件化设计使复杂系统更易维护和扩展，UniTask等异步编程库进一步提高了代码可读性与执行效率。

本文在此基础上，以实际项目为验证载体，探索五种玩法融合的完整技术方案。

## 第2章 相关技术

### 2.1 Unity游戏引擎

Unity引擎以"组件-游戏对象"（Component-GameObject）为核心设计范式，游戏对象通过挂载不同组件获得功能，天然支持组件化与模块化开发。其跨平台能力、丰富的资源商店和活跃的社区使其成为中小型团队的主流选择。核心概念包括：GameObject（场景实体）、Component（功能模块）、Prefab（可复用预制体）、Scene（内容容器）与Asset（资源管理）。

### 2.2 GameFramework框架

GameFramework是基于Unity的开源游戏开发框架，以模块化设计为核心理念，提供事件系统（Event）、实体系统（Entity）、UI系统（UI）、数据表系统（DataTable）、资源系统（Resource）和流程系统（Procedure）等标准化基础设施。框架将底层实现细节封装为简洁API，使开发者专注于业务逻辑，同时内置对象池、异步加载等性能优化机制。

### 2.3 多玩法融合游戏设计要素

Clash of Gods融合五种玩法：**RPG**提供角色成长框架；**Roguelite**通过随机性保证重玩价值；**搜打撤**带来探索中的风险与收益权衡；**自走棋**提供战前布阵与自动战斗的策略深度；**卡牌策略**增加战中改变战局的额外策略层次。

多玩法融合的核心设计要素是**玩法协同**——各系统通过有机联系形成完整循环：探索触发战斗，战斗奖励物品与卡牌，物品与卡牌强化战斗能力，形成自洽的正向循环。各系统通过事件驱动解耦，数据通过配置表驱动，保证各玩法可独立开发与快速迭代。

### 2.4 系统架构设计模式

**事件驱动架构**：组件间通过发布-订阅方式通信，不直接引用，降低耦合度。新功能只需订阅相关事件，不修改现有代码，可扩展性强。

**MVC模式**：模型层管理游戏数据，视图层负责UI显示，控制器层处理业务逻辑，实现职责分离，便于测试与维护。

**模块化与组件化设计**：将系统拆分为职责单一的独立模块，组件可跨项目复用，便于团队并行开发与问题定位。

### 2.5 配置表驱动设计

配置表驱动设计将游戏数据存储于Excel表格，程序通过接口读取，不硬编码任何游戏参数。其核心优势是**策划友好**——策划人员无需程序介入即可独立调整数值，数据修改不触发代码重编译，发布风险低，也便于测试人员独立验证。配置表设计遵循单一职责、字段规范、注释完善、ID分段等原则，确保数据结构清晰、引用关系明确。

## 第3章 需求分析

### 3.1 业务与用户需求

游戏面向喜好策略、探索与自走棋玩法的核心向玩家。玩家期望在单次游戏中体验到多维度的玩法——探索中的紧张感（搜打撤）、战斗的策略深度（自走棋+卡牌）、成长的持续满足感（RPG+Roguelite随机性）。

业务层面，系统需要解决多玩法融合开发面临的核心矛盾：系统耦合度高、数据管理效率低、扩展代价大、性能压力突出。

## 第4章 系统设计

### 4.1 系统总体架构设计

#### 4.1.1 分层架构

系统采用四层架构，各层单向依赖，上层依赖下层：

| 层次 | 内容 | 职责 |
|------|------|------|
| 基础框架层 | Unity引擎 + GameFramework | 渲染、物理、资源、对象池等底层能力 |
| 核心系统层 | Event / Entity / DataTable / UI / Procedure | 标准化服务接口，屏蔽底层实现 |
| 业务逻辑层 | 战斗 / 物品 / 卡牌 / 探索 / 配置模块 | 游戏特有业务，通过事件解耦通信 |
| 表现层 | UI界面 / 粒子特效 / 动画 / 音效 | 订阅事件被动更新，实现逻辑与表现分离 |

这种分层设计使业务系统无需关心底层渲染与资源细节，表现层无需了解业务逻辑，各层可独立迭代。

#### 4.1.2 模块划分与事件系统

各业务模块职责边界清晰：**战斗模块**负责战斗流程、AI决策、技能与Buff执行；**探索模块**负责场景敌人管理、视野检测与战斗发起；**物品模块**负责背包容器与装备效果；**卡牌模块**负责手牌与效果执行；**配置模块**为所有模块提供数据访问服务；**UI模块**通过订阅事件被动刷新，不直接调用业务模块。

模块间通信基于发布-订阅事件系统。事件参数类通过对象池管理生命周期，避免GC分配。发布支持立即触发（FireNow）和延迟一帧（Fire）两种模式，用于区分需要立即响应与可延迟处理的场景。游戏整体流程由有限状态机管理，在启动、预加载、主菜单、探索、战斗等流程间切换。

### 4.2 战斗系统设计

#### 4.2.1 整体架构

战斗系统采用三层结构：**流程控制层**管理战斗生命周期（准备/进行/结算）；**实体管理层**管理所有棋子实体的创建与销毁；**战斗逻辑层**包含AI决策、技能执行、命中检测、Buff管理、伤害计算等核心组件。

棋子实体采用组件化设计，持有属性组件、AI组件、战斗控制器、Buff管理器及技能实例，各组件职责单一、可独立替换。棋子初始化时根据配置表ID读取属性、创建技能实例、创建对应类型的AI组件。

#### 4.2.2 棋子属性系统

棋子属性分为**基础属性**（MaxHP、AttackPower、Defense、MagicResist、AttackSpeed、AttackRange、CriticalRate等，从配置表读取）和**衍生属性**（CurrentHP、FinalAttack等，运行时计算）。Buff对属性的修改通过属性修改器（AttributeModifier）实现，支持固定值加成与百分比加成，Buff移除时自动撤销修改器，所有属性变化触发事件通知UI更新。

#### 4.2.3 Buff系统

Buff系统是战斗中最复杂的子系统。IBuff接口定义标准行为契约：OnApply（施加时执行初始效果）、OnTick（每回合执行持续效果）、OnRemove（移除时撤销效果）、AddStack（增加层数）。BuffBase抽象基类实现通用的层数管理、持续时间管理与过期判断。具体Buff类型：

- **StatModBuff**：修改某项属性，通过AttributeModifier实现，支持固定值与百分比两种方式。
- **DotBuff**：每回合造成持续伤害（灼烧、中毒等）。
- **CCBuff**：控制类效果（眩晕、减速）。
- **ShieldBuff**：提供伤害吸收，耗尽后自动移除。

BuffManager以`Dictionary<int, IBuff>`（BuffID为键）存储活跃Buff，提供O(1)查询效率。Buff数据通过BuffTable配置，核心字段包括BuffType、Duration、MaxStack和JSON格式的EffectParams。

#### 4.2.4 技能系统

技能系统采用**策略模式**，将技能逻辑从战斗控制器中解耦，每个棋子的技能类独立实现IChessSkill接口。

**技能执行流程**：ChessAI触发攻击 → 播放攻击动画 → 动画关键帧事件触发 → ChessCombatController响应并调用技能类 → 技能类构建HitContext并调用命中检测器 → 检测器检测命中后计算伤害并应用效果。这一设计将伤害判定与动画帧精确同步，避免伤害提前或延迟触发的问题。

**命中检测系统**支持五种类型：瞬发单体（Instant）、近战挥砍（Melee）、投射物（Projectile）、范围AOE、射线穿透（Raycast），通过工厂类按需创建，分别对应不同的攻击形态。

#### 4.2.5 AI决策系统

棋子AI每帧执行决策循环：目标搜索（选取最近存活敌人）→ 冷却检查（冷却中则继续移动靠近）→ 距离判断（超出范围则移动，在范围内则攻击）→ 攻击执行（缓存目标，触发动画，重置冷却）。

**攻击缓存机制**是AI系统的关键设计：AI触发攻击时将目标缓存，动画事件触发时从缓存读取，避免动画播放期间目标死亡或移动导致的逻辑错误。配置表支持三种AI类型：RangedAI（远程，保持距离）、MeleeAI（近战，主动追击）、SupportAI（辅助，优先治疗血量最低的友方）。

#### 4.2.6 伤害计算系统

支持物理、魔法、真实三种伤害类型。物理/魔法伤害应用非线性减伤公式：**减伤率 = 防御力 / (防御力 + 100)**。防御100时减伤50%，防御200时约67%，防御400时约80%，收益递减，防止防御力堆叠过高导致免疫伤害。真实伤害不受防御影响，直接扣除HP。暴击在计算前判定，触发时伤害乘以暴击倍率。

#### 4.2.7 战斗触发与脱战机制

探索场景支持三种战斗触发方式：**偷袭**（玩家位于敌人背后、敌人低警觉时触发，玩家可选择施加Debuff）、**遭遇战**（正面接近未高度警觉的敌人时触发，玩家获得随机先手Buff）、**敌方先手**（敌人追上时触发，敌方获得先手Buff）。不同触发方式带来不同的初始优势，为探索行为赋予策略价值。

**脱战系统**：成功率 = 基础成功率 + 当前回合数 × 每回合加成（不超过上限）。成功后增加污染值并返回探索；失败则扣除当前HP的一定比例并进入冷却。脱战参数通过配置表管理，支持针对不同敌人类型设置不同难度。

### 4.3 物品与背包系统设计

#### 4.3.1 整体架构

物品系统采用继承体系：数据层以ItemBase为基类，衍生出ConsumableItem、QuestItem、TreasureItem、EquipmentItem四个子类；管理层包含背包管理器、装备管理器、宝物管理器；执行层包含效果执行器、词条生成器、羁绊检测器；UI层通过订阅事件被动刷新。物品ID采用分段设计（消耗品10000-19999、任务道具20000-29999、宝物30000-39999、装备40000-49999），便于快速判断物品类型。

#### 4.3.2 背包容器设计

背包以List存储Slot数据，每个Slot记录ItemId、Count、SlotIndex。AddItem优先叠加到现有格子，无法叠加则占用空格，背包满时触发提示事件返回失败；RemoveItem减少数量，归零则清空格子；SwapItems交换两格数据，同类可堆叠则尝试合并；SortItems按类型→品质排序。所有操作均触发对应事件通知UI。

#### 4.3.3 拖拽交互设计

拖拽支持背包内移动、背包↔装备槽、拖入丢弃区三类场景。状态机为Idle（待机）→ Dragging（原格子半透明、显示拖拽图标）→ Dropping（按目标类型执行操作）→ Idle。拖拽图标使用对象池管理，丢弃操作需二次确认防止误操作。

#### 4.3.4 词条与羁绊系统

**词条系统（Affix）**：宝物获得时从词条池（按Weight字段加权随机）抽取1-3个词条，数值在ValueRange范围内随机确定后固定不变，支持属性加成与特殊效果两种类型。

**羁绊系统（Synergy）**：装备/卸下宝物时统计所有已装备宝物的羁绊ID，达到RequireCount则激活对应效果。完全由配置表驱动，新增羁绊无需修改代码。

### 4.4 策略卡系统设计

策略卡系统由三个核心组件构成：**CardManager**管理手牌全生命周期；**CardEffectExecutor**以工厂字典将效果类型字符串映射到具体效果类，实现动态分发；**CardPool**按分层设计维护不同敌人类型对应的卡牌池，通过加权随机控制获取概率（普通敌人→普通/稀有卡牌，精英→稀有/史诗，Boss→史诗/传说）。

卡牌效果采用**命令模式**，ICardEffect接口定义统一的Execute方法。新增卡牌效果只需实现接口并在映射表中注册，无需修改现有代码，符合开闭原则。系统已实现12种效果，涵盖全体护盾、AOE伤害、单体治疗、全体强化、控制、吸血、冻结、复活等类型。

### 4.5 探索系统设计

#### 4.5.1 敌人AI状态机

敌人AI采用五状态有限状态机（Idle/Patrol/Alert/Chase/Combat），状态间转换条件由配置表参数（AlertDistance、ChaseDistance、CombatDistance等）驱动，支持不同敌人类型的差异化行为配置。精英敌人在追击开始时广播一次玩家位置，召集范围内其他敌人，每次追击只广播一次。

#### 4.5.2 视野检测系统

视野检测采用**双层机制**：圆形感知范围（听觉，半径8米，警觉增速0.5/秒）和扇形视觉范围（视觉，张角60度、距离12米，警觉增速0.75/秒）。警觉度是[0,1]浮点数，离开检测范围后以0.2/秒衰减，达到1.0时切换到Alert状态。这种双层设计模拟了现实中视觉比听觉更敏感的感知特点，使得玩家的接近方式（正面/背后/侧面）影响触发难度，增加了探索行为的策略性。

视野检测每0.15秒执行一次（而非每帧），使用NonAlloc物理API配合预分配缓存数组，在保证响应及时性的同时大幅降低检测开销。

#### 4.5.3 净化与奖励系统

战斗胜利后，若被击败敌人为可净化类型（Boss/Special且配置了卡牌ID），则显示净化UI，玩家确认后将对应卡牌加入手牌。净化操作可选，玩家可跳过直接返回探索。

### 4.6 数据表与配置系统设计

系统采用Excel → TXT → .bytes三阶段工作流：策划在Excel中编辑数据 → 工具自动生成C#数据类和.bytes二进制文件 → 运行时加载.bytes文件（速度快于文本格式）。**核心价值**是策划与程序完全解耦：策划修改数值无需触碰代码，也无需重编译，支持快速迭代。

将敌人探索属性（含AI参数与视野参数）与战斗属性分表存储，是基于单一职责原则的设计决策——探索系统与战斗系统各自只读取自己关心的数据。

为高频访问的配置表（BuffTable、ItemTable、CardTable等）实现静态缓存字典，首次查询时加载并缓存，后续直接读取，避免重复查询。泛型接口`GetRowById<T>`和`GetRowsWhere<T>`统一所有配置表的访问方式，保证类型安全。

### 4.7 UI系统设计

UI系统基于UIForm模式，分为界面管理层、界面逻辑层（继承UIFormBase，具备标准生命周期）和组件层（可复用组件通过对象池管理）。

UI组件引用通过自动生成的Variables脚本管理，OnInit时通过序列化字段直接赋值，无运行时Find/GetComponent开销。状态感知型界面在OnInit订阅事件、OnClose取消订阅，防止内存泄漏。UI动画统一使用DOTween，界面关闭时必须终止动画，防止对象销毁后动画继续执行导致空引用。

**战前准备UI**承担四项职责：棋子手牌以扇形排列支持点击选中展示属性；装备预览区从背包过滤实时展示；偷袭触发时展示三选一Debuff面板（选项错开弹出），先手Buff展示时开启5秒倒计时（超时自动选第一个，避免流程卡死）；准备倒计时读取配置表，归零自动进入战斗。

**战斗结算UI**：胜利分支延迟显示宝箱，动画关键帧触发奖励生成，每件物品依次弹出，全部展示后提供批量收取入口；失败分支自动计时返回探索，无需操作。所有异步操作通过CancellationTokenSource管理，界面关闭时立即取消。

### 4.8 本章小结

本章完成了Clash of Gods游戏系统的完整设计。核心设计原则：四层分层架构实现关注点分离；事件驱动解耦各业务模块；策略模式与命令模式使技能和卡牌效果可零侵入扩展；配置表三阶段工作流实现策划程序解耦；双层视野检测在仿真精度与性能开销之间取得平衡；Variables脚本生成消除运行时组件查找开销。

## 第5章 系统实现

### 5.1 技术美术系统实现

游戏采用Unity URP渲染管线，开启SRP Batcher与GPU Instancing，使相同棋子共享DrawCall，在多棋子战斗场景中效果显著。

实现三套自定义URP着色器：**描边着色器**采用两Pass方案，第二Pass将顶点沿法线外扩并仅渲染背面，实现稳定的选中高亮效果，性能开销极小；**溶解着色器**采样噪声贴图决定各像素是否丢弃（clip），边缘发光效果由DOTween驱动DissolveProgress参数，用于棋子死亡与场景过渡；**卡通渲染着色器**将漫反射分为三个色阶产生卡通效果，叠加边缘光增强立体感。

棋子动画状态机包含七个状态，移动使用混合树（Blend Tree）平滑过渡。**动画关键帧事件**是战斗与动画精确同步的关键机制：攻击动画命中帧处挂载事件，ChessCombatController响应后触发技能执行，保证伤害判定与动画帧完全一致，避免异步导致的伤害时机偏差。

粒子特效通过对象池预热常用实例，运行时从池中取用，消除战斗中因实例化导致的性能抖动。

### 5.2 战斗系统实现

战斗流程完全以UniTask异步驱动，分为准备、战斗、结算三个阶段。准备阶段按触发类型处理先手效果：偷袭时等待玩家选择Debuff，遭遇战/敌方先手时随机分配先手Buff并展示通知。战斗阶段每帧检测胜负，结算阶段清除所有Buff并发布结束事件驱动后续处理。所有异步方法通过GetCancellationTokenOnDestroy绑定对象生命周期，对象销毁时自动取消。

Buff系统的应用支持两种方式：**配置表方式**（在技能配置的BuffIds字段填写ID，命中时自动应用，适合无条件Buff）；**回调方式**（在技能的OnHitCallback中手动触发，适合条件Buff，如后羿持有特定Buff时才触发附加效果）。两种方式覆盖所有技能设计需求，且互不干扰。

AI决策每帧执行目标搜索和攻击判断，攻击时将目标缓存到成员变量，动画事件触发时从缓存读取，确保伤害作用于正确目标。棋子移动由NavMeshAgent驱动，速度参数从配置表读取。伤害计算应用非线性减伤公式，伤害结算后生成飘字并发布事件更新血条UI。

### 5.3 物品系统实现

物品工厂根据物品ID所在分段创建对应子类实例，无需手动判断类型。TreasureItem创建时额外执行词条生成（加权随机抽取、数值随机确定），词条数据随物品持久化到存档。

背包操作的边界情况（满背包、堆叠溢出）均在InventoryManager内部完整处理，UI通过事件被动刷新，不感知数据变化原因。拖拽系统实现三个拖拽接口，拖拽结束时通过EventSystem.RaycastAll检测放置目标并执行对应操作。装备宝物时触发羁绊检测，统计所有已装备宝物的羁绊ID，满足RequireCount则激活效果。

### 5.4 卡牌系统实现

手牌以卡牌ID列表存储于PlayerDataModel，支持存读档。CardEffectExecutor通过预注册工厂字典实现效果动态分发，效果类通过工具类统一访问战斗系统，屏蔽底层调用细节。

### 5.5 探索系统实现

敌人AI采用状态对象模式（每个状态封装为独立类），状态切换调用当前状态OnExit后再进入新状态OnEnter，状态间无直接依赖。视野检测以计时器降频执行，圆形检测使用NonAlloc版本复用缓存数组，扇形检测在此基础上增加角度判断，警觉度限制在[0,1]范围内。

战斗触发检测每0.1秒执行一次，满足条件时显示交互提示UI并监听玩家输入（通过PlayerInputManager），玩家确认后创建战斗触发上下文并通过事件通知流程切换场景。

### 5.6 数据配置系统实现

配置表在预加载流程中通过UniTask.WhenAll并行异步加载，最大化IO并行性，全部加载完成后才进入下一流程。高频配置表通过静态缓存扩展类减少重复查询，泛型接口统一访问入口，编译时保证类型安全。

### 5.7 性能优化策略

**CPU优化**：对象池预热消除运行时实例化开销；非关键逻辑降频更新（视野检测0.15s/次、战斗机会检测0.1s/次）；所有范围检测使用NonAlloc版本复用缓存数组，避免GC分配；条件编译限制日志只在编辑器模式执行。

**GPU优化**：UI动态合批；相同棋子GPU Instancing共享DrawCall；探索场景敌人LOD远距离面数降低50-70%；预烘焙光照贴图替代实时光照，大幅降低GPU开销。

**内存优化**：大型资源异步加载并及时卸载；DXT5/BC7纹理压缩降低内存占用50-70%；UI图标按功能模块打包为独立Sprite Atlas，按需加载。

### 5.8 本章小结

本章实现了系统设计中规划的全部模块。核心实现要点：UniTask异步编程统一了所有异步流程管理；动画关键帧事件机制保证了伤害与动画的精确同步；Buff双通道应用方式覆盖了所有技能设计需求；命令模式与工厂字典使卡牌效果可零侵入扩展；视野检测降频策略与NonAlloc检测在精度与性能间取得合理平衡；多维度优化手段保证了游戏在主流PC上的流畅运行。

本文围绕多玩法融合游戏Clash of Gods的设计与实现，完成了以下工作：

1. **系统架构设计**：采用四层分层架构，通过事件驱动实现模块解耦，通过配置表驱动实现数据与代码分离，形成了可扩展、可维护的架构方案。

2. **核心系统实现**：实现了基于自走棋机制的战斗系统（棋子AI、策略模式技能、完整Buff生命周期、非线性伤害计算）；支持多物品类型的背包系统（堆叠机制、拖拽交互、词条与羁绊）；基于命令模式的策略卡系统；具有五状态AI与双层视野检测的探索系统。

3. **技术实现**：采用UniTask统一异步编程，动画关键帧事件保证伤害与动画精确同步，对象池、LOD、纹理压缩等多维度优化保证了PC端的流畅运行。

4. **系统测试**：通过功能测试、性能测试、兼容性测试验证了系统的正确性与稳定性，52个测试用例全部通过。

**实现成果**：游戏功能完整，玩法循环自洽；采用现代化技术架构；高配中配PC稳定60 FPS，内存峰值350MB；模块化设计使新增内容的扩展成本极低。

### 7.2 主要贡献

**理论层面**：提出了RPG、Roguelite、搜打撤、自走棋、卡牌五种玩法有机融合的设计方案，为同类游戏提供了可参考的架构实践；总结了基于GameFramework框架的分层架构与事件驱动设计最佳实践；探索了配置表驱动开发在多玩法融合游戏中的应用模式。

**实践层面**：验证了技术方案的可行性；积累了Unity PC游戏开发的工程实践经验；产出了各功能模块的可复用代码资产。

### 7.3 存在的问题与改进方向

当前系统的主要局限性：视野检测仅基于距离和角度，未考虑障碍物遮挡，可能导致穿透检测；游戏内容量（棋子、物品、卡牌数量）有限，长期游戏体验有待丰富；低端设备复杂战斗场景的帧率仍有提升空间。

**改进方向**：添加射线检测验证视线，实现更真实的视野遮挡；增加AI记忆系统，敌人丢失玩家后保留一段时间的位置信息；通过更多测试与数据分析优化游戏数值平衡。

### 7.4 未来展望

**功能扩展**：引入实时或异步对战功能增加社交属性；增加更多棋子、物品、卡牌与地图丰富游戏内容；添加完整剧情系统与成就系统延长游戏生命周期。

**技术优化**：引入行为树或机器学习增强棋子AI智能性；进一步优化渲染管线；引入自动化测试框架提高测试效率与覆盖率。
